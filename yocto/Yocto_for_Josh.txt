#what is Yocto
===============
It is a build system - Generates Linux distribution - Kernel, libs and utils
It generates SDK for apps development. (we use the image-based sdk)
Supports thousands of linux packages (~10000), including modern technologies (latest GCC 7.x, Linux Kernel, virtualization, dockers, gRPC, etc)
The idea - Recipes organized in layers.

The general use case:
=====================
*Yocto SDK is built for the specific HW, an image-based SDK.
*This SDK is then installed by the developers on their host.
	Upon installation, the SDK is self extracted and the cross compile env is set.
*The application are easliy built in that env.
*The target Yocto rootfs along with the appications compose the final image. 

#the motivation for Yocto
=========================
*fully flexible, built from source, easy to add packages
*embedded specific:
	support cross compile, many CPU archetectures
 	embedded packages not inlcuded in desktops
*A linux foundation project
*open source
*self-contained
*bundle size was reduced within 100M
*simplified process - same build for local and TC
*supports QEMU

Yocto is not a fixed set but a base of tools, fully flexible.

#Cons:
======

*long build time - most of the build time is spent on building GCC toolchain and generic Linux
packages. Currently, Yocto image that is used for Agema products contains around 300 packages

#Yocto is OpenEmbedded Build System:
=================================== 
The core components of the Yocto Project are:

• BitBake, the build engine. It is a task scheduler, like make. It interprets
configuration files and recipes (also called metadata) to perform a set of tasks, to
download, configure and build specified applications and filesystem images.

• OpenEmbedded-Core, a set of base layers. It is a set of recipes, layers and classes
which are shared between all OpenEmbedded based systems.

• Poky, the reference system. It is a collection of projects and tools (with recipes), used to bootstrap
a new distribution based on the Yocto Project.

#A standard SDK consists of the following:
=========================================
The SDK includes the cross toolchain, the target sysroot, host sysroot, env scripts, other metadata and config.
	Cross-Development Toolchain: This toolchain contains a compiler, debugger, and various miscellaneous tools.
	Target sysroot: Libraries, Headers, and Symbols: The libraries, headers, and symbols are specific to the image (i.e. they match the image).
	Host sysroot: Matches the SDK host system (usually x86_64) and used by the yocto env itself, like: cmake, pkg-config, ...
	Environment Setup Script: This *.sh file, once run, sets up the cross-development environment by defining variables and preparing for SDK use.

#SDK self extraction upon installation:
=======================================

In a Yocto SDK .sh installer, the compressed tarball (usually a .tar.xz archive containing the SDK files) is literally appended to the end of the shell script.
Then a trick with "tail" is used at the first part of the script to untar and install it: tail -n +$ARCHIVE_START_LINE $0 | tar xJf - -C $INSTALL_DIR
This installer script is generated by the populate_sdk bitbake command.

#a yocto recipe
================
a file (with a .bb extension) that defines how to fetch, configure, build, and package a software component. Recipes are the fundamental building blocks of a Yocto build system
implemented in bitbake syntax - bash (usually for variable) and python (usually for tasks/ functions) and parsed by bitbake

example:
--------
SUMMARY = "MyApp - A simple example application"
DESCRIPTION = "This is a simple example application for Yocto."
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://LICENSE;md5=abc123..."

SRC_URI = "git://github.com/example/myapp.git;branch=main"
SRCREV = "abcdef1234567890"

S = "${WORKDIR}/git"

inherit cmake

DEPENDS = "boost"

do_install() {
    install -d ${D}${bindir}
    install -m 0755 myapp ${D}${bindir}/myapp
}

explanations:
--------------
SUMMARY / DESCRIPTION - Metadata for the package
LICENSE / LIC_FILES_CHKSUM - License info and checksum of license file
SRC_URI - Where to fetch the source code
SRCREV - Git commit hash or version
S - Source directory after unpacking
inherit - Inherit a class (e.g., cmake, autotools, cve-check)
DEPENDS - Build-time dependencies
do_install() - Custom install steps (optional)

in: meta-my-layer/recipes-example/myapp/myapp_1.0.bb

will be added with create-layer and add-layer

# A yocto class
================
(.bbclass extension) is a reusable set of build logic that can be shared across multiple recipes. 
loacted under meta/calsses. can be used by "inherit" in a specific recipe or in local.conf for all recipes

examples:
---------
base.bbclass - Core functionality for all recipes. every recipe inherits the base class.
autotools.bbclass - Adds support for GNU Autotools (configure, make, etc.)
cmake.bbclass - Adds support for CMake-based builds
cve-check.bbclass - Adds CVE vulnerability scanning
spdx.bbclass - Enables SPDX sBOM generation

#how the split is done
The PACKAGES and FILES variables controls splitting. 

#The PACKAGES variable
lists all of the packages to be produced

#The FILES variable
the list of directories or files that are placed in packages.
a space-separated list of files or paths that identify the files you want included as part of the resulting package.

For example, FILES_${PN} specifies the files to go into the main package. PN = recipe name.

example:

     FILES_${PN} += "${bindir}/mydir1/ ${bindir}/mydir2/myfile"


The order of the PACKAGES value is significant. For each installed file, the first package whose FILES value matches the file is the package into which the file goes.
Package variables can be found in:oe-workdir/pkgdata

PACKAGES and FILES values can be found under oe-workdir/pkgdata/ipmitool
PACKAGES - The list of packages to be created from the recipe. The default value is the following:

     ${PN}-dbg ${PN}-staticdev ${PN}-dev ${PN}-doc ${PN}-locale ${PACKAGE_BEFORE_PN} ${PN}

#patching
The do_patch task uses a recipe’s SRC_URI statements and the FILESPATH variable to locate applicable patch files.
During the build process, BitBake searches each directory in FILESPATH in the specified order when looking for files and patches specified by each file:// URI in a recipe’s SRC_URI statements.

SRC_URI is per recipe.
FILESPATH is inherited by a recipe. do not edit.

FILESPATH
The default set of directories the OpenEmbedded build system uses when searching for patches and files.

#When adding a new package to yocto:
=====================================
first we should decide if it deserves a separate layer or not (by size and modularity)
If a new layer is required, then use a bitbake to create the layer:

bitbake-layers create-layer ~/mrv_dev/init-kconfig/ybld/poky/meta-mylayer

note: it is used with full path.

Once you create your general layer, you must add it to your bblayers.conf file. 
Adding the layer to this configuration file makes the OpenEmbedded build system aware of your layer so that it can search it for metadata.

bitbake-layers add-layer ~/mrv_dev/init-kconfig/ybld/poky/meta-mylayer

make sure it is added successfully:
bitbake-layers show-layers
or check bblayers.conf

After the layer is adde successfully, it can be built using devtool modify.

what packages are included in the final image? learned for SBOM generation
===========================================================================
bitbake -e core-image-full-cmdline -c do_rootfs | grep "^IMAGE_INSTALL" | tr ' ' '\n' | sed '/^$/d' 
this is not sufficient because Yocto uses dependency resolution and package splitting, so the final image includes:

	Packages from IMAGE_INSTALL and CORE_IMAGE_EXTRA_INSTALL
	Dependencies of those packages (automatically pulled in)
	Runtime dependencies (RDEPENDS)
	Split packages (e.g., a recipe might produce multiple packages like foo, foo-dev, foo-doc, etc.)

So, the actual image may contain many more packages than those listed in IMAGE_INSTALL.

more reliable way is the manifest file and the buildhistory files that are generated the files along the build process

#create-spdx:
==============
use the spdx class
yocto generates all SBOM files under tmp/deploy/spdx
for all relevant recipes that are used for the image, it will create one spdx file per recipe, containing metadata like: Source files, Licenses, Checksums, Package relationships
it also creates the spdx summry file about the enitre image

bitbake core-image-full-cmdline -c create_spdx

#cve-check:
===========
do the check like blackduck or loadpress
for all relevant recipes that are used for the image, it will check each recipe for known Common Vulnerabilities and Exposures (CVEs) against the NVD (National Vulnerability Database) or other CVE databases.
Produces output files under tmp/deploy/cve containing: CVEs found per package, Summary of all CVEs, CVEs grouped by severity or status
Output is typically in .txt and .csv formats. JSON output is available in newer Yocto versions (e.g., Kirkstone and later) with CVE_CHECK_FORMAT = "json".

bitbake core-image-full-cmdline -c cve_check
